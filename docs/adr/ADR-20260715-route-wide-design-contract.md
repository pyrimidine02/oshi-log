# ADR-20260715: 전체 라우트 Urban Travel Field Notes 디자인 계약

## 상태

Accepted — 2026-07-15

## 배경

Urban Travel Field Notes 1차 재설계는 홈·탐방·이벤트·도감·유저 상세의
핵심 흐름을 새로 만들었다. 그러나 `app_router.dart`의 63개 `GoRoute`를
추적하면 36개 실제 페이지 클래스로 수렴하며, 동일한 도감·방문 기록도
어느 경로로 진입하는지에 따라 신규 Field 화면과 구형 카드 화면이 다르게
열렸다. 인증, 설정, 작품·멤버·음악 상세, 검색, 알림, 배너 선택,
커뮤니티 작성기도 서로 다른 상단바·그라디언트·글래스·카드 문법을
사용했다.

색상 토큰만 같게 바꾸는 것으로는 사용자가 페이지를 이동할 때마다 다른 앱을
사용하는 느낌을 해결할 수 없다. 따라서 실제 라우터에 연결된 모든 화면을
하나의 제품 문법으로 수렴하되, API·provider·라우트·권한 계약은 보존한다.

## 범위 판정

- 기준은 `lib/core/router/app_router.dart`에서 실제로 builder되는 화면이다.
- 홈·탐방·일정·정보·커뮤니티·마이 루트와 모든 상세·오버레이·인증·
  설정 라우트를 포함한다.
- 라우팅되지 않는 구형 sibling(`home_page.dart`, `explore_page.dart`, 구형
  `calendar_page.dart`, 구형 피드·마이 페이지 등)은 이번 시각 이전 대상에서
  제외한다. 사용자에게 노출되지 않는 코드를 굳이 다시 디자인하지 않는다.

## 결정

### 1. 공통 페이지 크롬

- 메인 5탭 하단바의 실루엣·순서와 커뮤니티 전용 하단바는 사용자 결정대로
  유지한다.
- 독립 라우트는 따뜻한 paper 배경의 56dp `gbtStandardAppBar`를 사용한다.
  고도·블러·대형 확장 영역 대신 0.8–1px 규칙선으로 본문과 구분한다.
- 전체 페이지 검색은 따로 뜨는 글래스 헤더가 아니라 공통 상단바 내부에 배치한다.
- 오류·빈 상태·라우트 복구는 `GBTEmptyState` 계열로 표준화한다.

### 2. 문서형 정보 위계

- 페이지는 필요할 때 `eyebrow → title → description`의 `GBTPageHeader`로
  맥락을 설명한다. 상단바 제목과 같은 대형 제목을 반복하지 않는다.
- 상세 화면의 대형 이미지는 핵심 정보를 밀어내지 않도록 한 개만 유지하고
  16:9 비율·약 220dp 이내를 기본으로 한다. 이미지가 없으면 큰 가상 포스터를
  만들지 않는다.
- 반복 데이터는 둥근 카드 격자 대신 날짜·번호·상태 레일과 얇은 규칙선을
  사용한 borderless row로 표현한다.
- 티켓은 실제 이벤트·일정, 스탬프는 완료한 방문, 앨범 그라디언트는 실제
  커버 가독성처럼 도메인 의미가 있는 경우에만 유지한다.

### 3. 색상·상태·제어

- 기본 선택·이동·작성 행동은 기존 GBT blue, 장소·방문 메타는 teal을 사용한다.
- 빨강은 삭제·탈퇴·신고 위험·오류·취소된 일정과 같은 의미로 제한한다.
  Google·Apple 로고 등 외부 브랜드 색은 예외로 보존한다.
- 로컬 모드 선택기는 글래스·그림자를 제거한 평면 paper track과 blue 선택면을
  사용한다. 전역 하단바와 또 하나의 큰 내비게이션으로 보이지 않게 한다.
- 모든 실행 제어는 44–48dp 이상을 유지하고, 320dp 너비·200% 텍스트에서
  표현을 줄이기보다 줄바꿈·스크롤·열 수 조정으로 해결한다.
- 앱이 `MediaQuery.textScaler`에 별도 상한을 씌우지 않는다. 사용자의 플랫폼
  접근성 설정을 그대로 따르고, 고정 높이 하단 내비게이션은 실제 라벨 배율에
  맞춰 필요한 범위에서만 높이를 늘린다.

### 4. 라우트 수렴과 기능 보존

- `/visits`와 `/live-attendance`는 구형 `VisitHistoryPage` 대신 탐방 내부와 같은
  `FieldVisitLedgerPage`를 연다.
- `/zukan`은 구형 2열 카드 그리드 대신 `FieldZukanArchivePage`를 연다.
- 페이지 없음·잘못된 라우트 인수도 공통 상단바와 복구 상태를 사용한다.
- 시각 이전 중 API·provider·autosave·필터·좋아요·북마크·신고·출석·라우팅
  계약을 바꾸지 않는다. 동작하지 않는 장식 버튼은 제거하지만 실제 동작은 유지한다.

## 화면군별 적용

| 화면군 | 적용 결정 |
| --- | --- |
| 홈·탐방·일정·정보·마이·커뮤니티 | 신규 Field 루트와 기존 하단바 유지 |
| 인증·설정·계정 | 파란 여정 헤더, borderless 설정 section/row, 파괴적 행동만 error 색 |
| 작품·멤버·성우·음악 | 대형 gradient hero를 dossier 헤더와 indexed row로 전환 |
| 응원·명대사·칭호·덕력·즐겨찾기 | 카탈로그 카드를 문서형 색인과 얇은 규칙선으로 전환 |
| 장소·방문 상세·통계 | 300dp hero·premium dashboard를 실제 정보 우선 필드 노트로 전환 |
| 검색·알림·뉴스·연결·북마크 | 컴팩트 크롬과 borderless 정보 행 |
| 배너·그리드 | 고정 3열 대신 320dp 1열, 일반 폰 2열, 광폭 3열 반응형 정책 |
| 작성·수정·게시글·여행 후기 | autosave와 기능은 보존하고 글래스·pill 중심 작성기를 선형 문서 작성기로 전환 |
| 내부 운영 | 고정 2열 대시보드를 반응형 운영 원장과 상태 행으로 전환 |

## 고려한 대안

### 전역 테마만 변경

가장 빠르지만 정보 순서, 대형 헤더, 중첩 카드, 고정 그리드가 남는다. 전면
재설계 요청을 충족하지 못해 선택하지 않았다.

### 모든 화면을 같은 카드 대시보드로 통일

일관성은 쉽게 얻지만 장소, 일정, 작품, 커뮤니티의 정보 단위가 평준화된다.
공통 크롬·타이포·색·간격은 통일하되 도메인별 티켓·원장·표본 표현은 제한적으로
남긴다.

### 라우팅되지 않는 구형 페이지까지 모두 재작성

실제 제품 품질에 영향을 주지 않고 회귀 면을 늘린다. 라우트를 기준으로 완결하고
신규 sibling의 패리티가 확인된 뒤 별도 정리한다.

## 영향과 검증

- 디자인 계약은 라우트 호환성과 사용자 기능 계약을 변경하지 않는다.
- 위젯 테스트는 320dp·200% 텍스트, 다크 모드, 44–48dp 터치, 스크린리더
  선택·버튼 의미를 주요 가드레일로 삼는다.
- 메인·커뮤니티 하단바, 공통 상단바, 프로젝트 선택 행, 검색 기록과 작성·삭제
  제어를 위 조건에서 직접 측정한다. 알림 이동은 알림 도메인의 라우트 해석기를
  단일 진실 공급원으로 두고 임의의 구형 화면 폴백을 만들지 않는다.
- iOS 시뮬레이터에서 홈과 하단바, 프로젝트 전환, 실제 이벤트·장소 데이터를
  먼저 확인한다. 전체 라우트 시각 QA는 iOS·Android 각 1기기 이상에서 후속한다.
- 여행 후기 작성·상세의 현재 mock 저장·더미 데이터는 시각 이전으로 실제 계약이
  되지 않는다. 본 작업에서 새 mock을 추가하지 않고, 실제 API 계약 작업을
  `TODO.md`에 분리한다.
